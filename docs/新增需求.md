    - 导入导出的文件目录如下
```
多文章导入导出
articles.zip
├── article1/           //导出时文件夹名称一般为文章的slug。导入时，文件夹名称不影响导入结果，导入时会根据article.json中的slug进行导入
│   ├── article.json
│   ├── article.md
│   └── image/
│       ├── cover.jpg   //文章头图，可选。如果是外链则在article.json中指定url即可
│       └── article/
│           ├── xxx.jpg   // 媒体资源，文件名、文件格式不影响导入导出，但 MIME 类型需在常见媒体资源范围内
│           └── ...
├── article2/
└── ...

单文章导入导出
article.zip             //导出时压缩包名称一般为文章的slug。导入时，压缩包名称不影响导入结果，导入时会根据article.json中的slug进行导入
├── article.json
├── article.md
└── image/
    ├── cover.jpg       //文章头图，可选。如果是外链则在article.json中指定url即可
    └── article/
        ├── xxx.jpg       // 媒体资源，文件名、文件格式不影响导入导出，但 MIME 类型需在常见媒体资源范围内
        └── ...
```
    - `article.json` 包含文章除正文、媒体资源外的其他数据，例如标题、slug、分类/标签的名称及slug、发布时间、状态、外链头图（如果存在）等等所有元数据
    - 导入时，将 `article.json` 中的元数据导入到数据库中，将 `article.md` 中的内容导入到文章正文中，将 `image/cover.jpg`（如果存在） 导入媒体资源并用作文章头图，将 `image/article/` 中的所有媒体资源导入媒体资源中，并且将文章内容中的媒体资源路径（全部形如 `![xxx](image/article/xxx.xxx)`）进行替换，替换为导入后的媒体资源路径
    - 导入时，多文章包里如果有非文章目录、隐藏文件、__MACOSX 等，建议忽略；如果目录内缺 article.json / article.md 再报错。
    - 导入时，如果文章的slug已经存在，或导入文章列表内存在slug重复，则直接提示导入失败
    - 导入时，如果文章的分类或标签不存在，则自动创建分类或标签，描述为空
    - 导入时，直到导入成功前，所有文章的所有数据（包含媒体数据，文章内容，文章元数据等等所有数据）都不会保存到数据库中，导入失败则不保存任何数据
    - 导入时，只处理媒体资源路径的替换，其他链接不做处理
    - 导入时，如果既没有 image/cover.jpg，也没有外链头图 URL，则文章头图为空。
    - 导入时，如果同时存在 image/cover.jpg 和 article.json 中的外链头图 URL，则直接抛出错误
    - 导入时，若存在未被引用的图片，则直接导入媒体资源
    - 导入时，所有文章作者都为当前登录用户
    - 导入时，安全校验：zip 导入需要防 Zip Slip 路径穿越、超大 zip、压缩炸弹、非法文件类型、文件大小限制。
    - 导入失败时，弹窗提示导入失败，并且显示失败的原因，例如具体哪一篇文章导入失败等等，对多种可能性做好异常处理
    - 可参考的导入失败原因：article.json 缺失或格式非法；article.md 缺失；slug 已存在，导入文章列表内存在slug重复；分类/标签字段非法或创建失败；正文引用的本地媒体文件不存在；媒体文件导入失败
    - 导入成功时，弹窗显示导入成功的文章列表
    - 导出时，将选中的文章的所有数据按格式导出为zip压缩包
    - 导出时，一并打包文章涉及到的所有本地媒体资源，包括头图和正文中引用的图片，可以保持原有文件名，文件格式不变。但是要处理文章内部的媒体资源路径，导出时将文章内容中的媒体资源路径进行替换，替换为导出后的媒体资源路径（全部形如 `![xxx](image/article/xxx.xxx)`）
    - 导出失败时，弹窗提示导出失败，并且显示失败的原因，例如具体哪一篇文章因为什么原因导出失败等等，对多种可能性做好异常处理
    - 导出成功时，直接通过浏览器下载导出后的zip压缩包，多篇文章命名为 `articles.zip`，单篇文章命名为 `{slug}.zip`

## 工作流程

需求列表中通过二级标题区分多个**部分**的需求，每一**部分**都包含多个需求，每个需求按如下工作流进行：

1. 先梳理该需求的具体要求，明确目的、需求是否清楚，有疑问的部分自行分析并提出问题，自行给出最推荐的解决方案
2. 如果涉及到早期doc文档内描述的内容变动，及时在文档中修改，保持doc文档的准确性
3. 开始按计划进行开发/修复，完成后，进行git提交，提交时排除 `docs\新增需求.md` 该文件
4. 进行测试，判断当前是否完成开发或修复，是否存在问题，如果存在问题重新回到第三步，如果没有问题进入下一步
5. 在 `docs\新增需求.md` 该文档中标记需求完成，然后进入下一个需求工作流，重新回到第一步操作

每次以一个**部分**为单位，全部结束后，询问用户是否进入下一个部分。

每个部分中所有需求依次进行，完成一个需求后直接进入下一个需求的工作流

## 开发约束

- 遵循最佳实践和设计模式，确保代码的可读性和可扩展性
